# Proposal：T-018 真实站点试用方案

**日期**：2024-11-03  
**基于**：research.md 调研结论  
**用户确认**：目标站点为内部业务系统，直接进入 T-018，不先修复已知技术债务

---

## 一、目标与约束

### 1.1 T-018 原始要求

> 2–3 个真实 Web 应用的小范围试用，记录失败、接管、耗时和用量

### 1.2 成功标准（基于 v0.1 验收经验）

1. **可观察性**：每次试用有完整的运行记录（runId、stepId、actionId、耗时、状态、证据、模型调用）
2. **失败分类**：明确区分框架缺陷 vs 模型决策问题 vs 站点不兼容
3. **副作用校验**：零未授权副作用（需要 oracle 或人工复核）
4. **接管指标**：记录确认次数、接管原因、是否误判
5. **性能与成本**：记录观察耗时、模型调用次数、token 用量（如果提供方返回）

### 1.3 约束

- 内部业务系统（可重置测试账号、已知业务流程）
- 当前 v0.1 不支持多标签页、跨域 iframe、文件上传、支付、密码/验证码自动输入
- Q-005 未闭合（用户/程序输入归因不可靠，保守暂停）
- 模型端点：DeepSeek 已验证，其他提供方需复验

## 二、方案对比

### 方案 A：垂直深入 — 单系统多场景深度验收（推荐）

**做法**：
1. 选择**一个**内部业务系统（如工单系统、OA 审批、内部 CRM）
2. 设计 **3–5 个**典型场景（查询、筛选、表单填写、审批、数据提取）
3. 每个场景运行 **5 次**，记录成功率、失败原因、接管次数
4. 建立该系统的 **oracle 校验机制**（数据库/API 查询验证实际副作用）
5. 产出：
   - 单系统适配报告（支持的控件、已知限制、规避方案）
   - 失败分类表（框架缺陷 vs 模型问题 vs 站点特性）
   - 性能基线（p50/p90/p95 观察耗时、平均步数、平均模型调用次数）
   - 一份可复现的测试套件（类似 fixture，但真实系统）

**改动范围**：
- 新增 `fixtures/real/<system-name>/`：场景定义、oracle 校验脚本、测试账号配置（不提交密钥）
- 新增 `specs/001-browser-agent/t018-report.md`：试用报告模板
- 可能微调 `packages/browser-chrome/src/document.mts`：观察器兼容新控件
- 可能微调 `packages/policy/src/index.mts`：站点规则调整

**优点**：
- **深度验证**：真正覆盖一个系统的完整流程，建立可重复的验收基线
- **可持续**：下一阶段可直接扩展场景或作为回归套件
- **风险可控**：单系统熟悉度高，oracle 容易建立，副作用可精确校验
- **适合 v0.1 → v0.2 过渡**：为后续扩展到更多站点建立模板

**缺点**：
- **覆盖广度有限**：只验证一种站点类型，对其他站点的泛化能力未知
- **前期投入较大**：需要先调研系统、设计场景、建立 oracle

**风险**：
- 选择的系统恰好是"最简单"的，后续扩展遇到更复杂站点时失败率激增
- 系统升级导致控件/流程变化，oracle 失效

---

### 方案 B：水平铺开 — 多系统单场景广度验证

**做法**：
1. 选择 **3 个**不同类型的内部业务系统（如工单、OA、BI 报表）
2. 每个系统设计 **1–2 个**最典型场景（如"创建工单"、"审批流程"、"数据导出"）
3. 每个场景运行 **3 次**，记录成功/失败、接管次数、耗时
4. **不建立完整 oracle**，依赖人工复核副作用（截图 + 日志）
5. 产出：
   - 跨系统兼容性矩阵（控件类型、框架版本、是否成功）
   - 失败模式分类（引用失效、观察不足、策略误判、模型幻觉）
   - 泛化能力评估（哪些能力是通用的，哪些需要针对性适配）

**改动范围**：
- 新增 `specs/001-browser-agent/t018-cross-system.md`：跨系统试用报告
- 可能微调观察器、策略分类（发现通用问题）
- 不建立完整 fixture，靠日志 + 人工复核

**优点**：
- **广度优先**：快速验证框架对不同站点的泛化能力
- **快速发现瓶颈**：哪类站点最容易失败，哪些控件最不兼容
- **适合 v0.1 对外展示**：证明框架不局限于特定站点

**缺点**：
- **深度不足**：每个系统只验证 1–2 个场景，可能遗漏复杂流程问题
- **副作用校验弱**：依赖人工复核，无法精确验证业务效果
- **不可重复**：无 oracle，后续回归需要重新人工检查

**风险**：
- 三个系统都"部分成功"，但没有一个能建立完整信心
- 失败分类不够精确（因为没有深入单个系统）

---

### 方案 C：混合渐进 — 1+2 模式（推荐平衡）

**做法**：
1. **阶段 1（1 周）**：选择**一个**核心系统（如工单），设计 **3 个**场景，建立完整 oracle，运行 **5 次**
   - 产出：单系统适配报告、可复现测试套件、失败分类表
2. **阶段 2（1 周）**：选择**另外 2 个**系统，每个 **1 个**场景，运行 **3 次**，人工复核
   - 产出：跨系统兼容性矩阵、泛化能力评估
3. **阶段 3（可选）**：根据阶段 1+2 的失败模式，优先修复最高频问题，回归验证

**改动范围**：
- 阶段 1：`fixtures/real/<core-system>/` + oracle + 测试套件
- 阶段 2：`specs/001-browser-agent/t018-phase2.md` + 日志分析
- 阶段 3：针对性修复（可能涉及 browser-chrome/policy/runtime）

**优点**：
- **深度 + 广度兼顾**：核心系统深度验证，其他系统广度覆盖
- **风险梯度递增**：先在可控系统建立信心，再扩展
- **迭代友好**：阶段 2 的失败可以指导阶段 3 的修复方向
- **适合团队协作**：阶段 1 和阶段 2 可以部分并行

**缺点**：
- **时间较长**：2 周以上（如果包含阶段 3）
- **需要多个系统的测试账号**：协调成本

**风险**：
- 阶段 1 选择的核心系统过于简单，阶段 2 失败率很高

## 三、方案对比表

| 维度 | 方案 A：垂直深入 | 方案 B：水平铺开 | 方案 C：混合渐进 |
| --- | --- | --- | --- |
| **系统数量** | 1 个 | 3 个 | 3 个（1 深 + 2 浅） |
| **场景数量** | 3–5 个 | 3–6 个（每系统 1–2 个） | 5 个（核心 3 + 其他各 1） |
| **运行次数** | 15–25 次 | 9–18 次 | 15–21 次 |
| **oracle 校验** | 完整 | 无（人工复核） | 核心系统有 oracle |
| **副作用验证** | 精确（数据库/API） | 弱（截图 + 日志） | 核心系统精确，其他弱 |
| **可重复性** | 高（可作回归套件） | 低（依赖人工） | 核心系统高，其他低 |
| **泛化能力评估** | 弱 | 强 | 中等 |
| **时间估算** | 1–2 周 | 1 周 | 2–3 周 |
| **风险** | 泛化能力未知 | 深度不足 | 时间较长 |
| **适合场景** | 为 v0.2 建立基线 | 快速对外展示 | 平衡深度与广度 |

---

## 四、推荐方案与理由

### 推荐：**方案 C（混合渐进）**

**理由**：
1. **符合 v0.1 验收哲学**：T-014 也是先深度验证 fixture 场景（各 5/5），再扩展到人工检查
2. **风险递增**：阶段 1 建立信心，阶段 2 暴露问题，阶段 3 针对性修复
3. **可交付性强**：阶段 1 完成后可以独立交付单系统适配报告，阶段 2 补充泛化评估
4. **为未来铺路**：核心系统的 oracle 和测试套件可以作为 v0.2 的回归基线

**备选：**
- 如果**时间紧张**（只有 1 周），选择**方案 A**：至少有一个系统的完整验证
- 如果**对外展示优先**（需要证明泛化能力），选择**方案 B**：快速覆盖多个系统

## 五、具体实施步骤（方案 C）

### 阶段 1：核心系统深度验证（1 周）

**目标**：建立第一个真实系统的完整验证基线

1. **系统选择**（0.5 天）
   - 调研 2–3 个候选系统（工单、OA、CRM）
   - 评估标准：可重置测试账号、已知业务流程、控件类型覆盖、oracle 可行性
   - 产出：选择报告（1 页，说明选择理由）

2. **场景设计**（1 天）
   - 设计 3 个典型场景：
     - 场景 1：查询 + 详情进入（类似 fixture search）
     - 场景 2：筛选 + 数据提取（类似 fixture table）
     - 场景 3：表单填写 + 提交确认（类似 fixture form）
   - 每个场景定义：目标、完成条件、oracle 校验方式
   - 产出：`fixtures/real/<system-name>/scenarios.md`

3. **Oracle 建立**（1 天）
   - 编写 oracle 校验脚本（数据库查询/API 调用/日志解析）
   - 测试 oracle 独立可用（不依赖 Agent 运行）
   - 产出：`fixtures/real/<system-name>/oracle.mjs`

4. **首次运行**（1 天）
   - 每个场景运行 1 次，记录完整日志（journal + events + 截图）
   - 人工复核：是否达成目标、副作用是否符合预期
   - 产出：首次运行报告（成功/失败、观察到的问题）

5. **迭代修复**（1.5 天）
   - 针对首次失败，分类：
     - 框架缺陷（观察器、控制层、策略）→ 修复代码
     - 模型决策问题（提示词、schema）→ 调整配置
     - 站点不兼容（不支持的控件）→ 记录限制
   - 每个场景运行 5 次，记录成功率
   - 产出：修复记录 + 5 次运行结果

6. **报告产出**（1 天）
   - 单系统适配报告：支持的控件、已知限制、规避方案
   - 失败分类表：框架缺陷 vs 模型问题 vs 站点特性
   - 性能基线：p50/p90/p95 观察耗时、平均步数、平均模型调用次数
   - 产出：`specs/001-browser-agent/t018-phase1.md`

### 阶段 2：跨系统广度验证（1 周）

**目标**：验证框架对不同站点的泛化能力

1. **系统选择**（0.5 天）
   - 选择另外 2 个系统，标准：控件类型差异大、业务逻辑不同
   - 每个系统设计 1 个典型场景
   - 产出：系统清单 + 场景定义

2. **运行与记录**（2 天）
   - 每个场景运行 3 次
   - 记录：journal + events + 截图 + 人工复核副作用
   - 产出：运行日志（6 次）

3. **跨系统分析**（1.5 天）
   - 兼容性矩阵：控件类型、框架版本、是否成功
   - 失败模式分类：引用失效、观察不足、策略误判、模型幻觉
   - 泛化能力评估：哪些能力是通用的，哪些需要针对性适配
   - 产出：`specs/001-browser-agent/t018-phase2.md`

4. **综合报告**（1 天）
   - 合并阶段 1 + 阶段 2 的结论
   - 优先级排序：哪些问题最高频、影响最大
   - 下一步建议：是否需要阶段 3 修复，还是直接进入 v0.2
   - 产出：`specs/001-browser-agent/t018-report.md`

### 阶段 3（可选）：针对性修复与回归（1 周）

**触发条件**：阶段 2 失败率 > 30% 且失败模式集中

1. **问题优先级排序**（0.5 天）
2. **修复实施**（3 天）
3. **回归验证**（1.5 天）：重新运行阶段 1+2 的场景
4. **更新报告**（1 天）

## 七、需要明确的前置条件

1. **测试账号**：
   - 核心系统：可重置测试账号 + 测试数据环境
   - 其他 2 个系统：只读测试账号（如果场景只涉及查询/筛选）

2. **Oracle 访问**：
   - 核心系统的数据库/API 访问权限
   - 或者：日志查询权限、管理后台查看权限

3. **模型配置**：
   - DeepSeek API 密钥（已验证）
   - 或者：其他兼容 Chat Completions 的端点

4. **时间预算**：
   - 方案 A：1–2 周
   - 方案 B：1 周
   - 方案 C：2–3 周（阶段 1+2 必须，阶段 3 可选）

## 八、风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 核心系统选择不当（过于简单） | 阶段 1 前调研 2–3 个候选，选择控件类型最丰富的 |
| Oracle 建立困难（无数据库访问） | 备选方案：API 查询、日志解析、管理后台截图对比 |
| 首次运行失败率 100% | 降级到 fixture 类似场景，先验证基础能力 |
| 模型调用成本过高 | 设置预算上限（如每场景最多 20 次模型调用），超限视为失败 |
| 站点规则变化导致失败 | 固定测试环境版本、记录环境指纹（URL/版本号/控件列表） |
