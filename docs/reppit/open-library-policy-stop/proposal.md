# 方案：定位 Open Library 的 POLICY_STOP

基于 [research.md](research.md)。目标是获得可验证的具体策略原因，并据此决定后续是否需要修复。现有两次事件不能证明具体原因；任何方案都不应直接放宽策略或自动重放动作。

## A. 临时诊断探针

- 做法：在受控测试环境中针对策略网关与运行时边界添加临时脱敏诊断，重新执行真实页面任务，记录动作类型、策略类别和原因；不记录输入值、页面原文或密钥。完成诊断后移除探针。
- 涉及：策略、运行时及必要的试用脚本；真实试用需要用户现有浏览器会话和模型配置。
- 优点：针对当前问题，用户界面和持久数据协议无需长期扩展。
- 缺点：需要再复现一次；模型可能选不同动作，临时探针也可能漏掉其他上下文原因。
- 风险：诊断信息即使脱敏也需限制范围；临时探针必须清理并验证。

## B. 持久化受限原因并在侧边栏显示（推荐）

- 做法：将策略结果中预先允许的类别与原因码传入现有运行时事件，侧边栏显示清楚的暂停原因和下一步提示；不存储输入内容、目标文本、页面原文或完整 URL。未知原因采用通用提示。再在真实页面重新试用，以得到该次运行的原因。
- 涉及：策略结果与运行时事件/协议、SDK或扩展宿主的事件转换、侧边栏和相关测试；以实际数据流确定具体文件。
- 优点：未来站点也可诊断，用户无需开发者工具；可保持原有授权和拦截语义。
- 缺点：改动跨模块，需要兼容旧历史记录及事件消费者；新增显示无法反推出已经发生的两次运行的原因。
- 风险：需严格限定可持久化原因，测试权限、脱敏和恢复行为；再次试用仍可能遇到不同动作。

## C. 只读页面上下文调查

- 做法：在独立浏览器会话中采集 Open Library 首页的观察截断情况和候选搜索框策略上下文，再用现有分类接口分析；不调用模型或改变插件。
- 涉及：浏览器探针及现有观察器/策略测试工具；结果与用户原会话分开记录。
- 优点：不需要 API 密钥，适合先检查页面特性，改动和费用较小。
- 缺点：不知道模型实际选择的动作和目标，页面与会话状态可能不同；即便找到潜在拦截也不能证明原故障原因。
- 风险：将模拟上下文误判为原运行证据；浏览器或站点环境可能阻碍复现。

## 推荐与边界

推荐 **B**：问题不仅是当前暂停，现有用户界面也缺少区分原因的信息。方案应先证明记录和展示真实策略决定，再以新的真实试用定位原因；定位后另行提出针对性修复。A 适合只想尽快排查本次故障，C 适合先做无模型、只读的页面调查。

无论选择哪项，暂不修改策略阈值、白名单或批准规则；不保证重跑后模型会选择同一操作；已有历史无法补回未保存的原因。需要用户选择方案，再进入计划阶段。
