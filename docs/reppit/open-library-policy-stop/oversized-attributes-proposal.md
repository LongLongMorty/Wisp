# 方案：安全处理目标元素的超长属性

基于 [追加调研](research.md)：在独立 Chrome 会话里，Open Library 的“搜索”按钮因 `data-i18n-ui` 为 3,186 字符而触发 2,048 字符属性上限；移除该属性的对照实验使结果从 `handoff` 变为 `confirm`。用户原任务的具体目标没有记录，不能证明两者完全一致。

## 共同边界

- 不绕过 `complete`、来源授权、敏感操作检查或确认；搜索按钮仍按现有规则要求用户确认。
- 目标或表单属性变化须继续改变目标指纹并使旧确认失效；不得简单忽略、截断超长值或将属性名当作安全证明。
- 限制单项及总处理量，超过上限仍标记不完整；不将原始属性值写入日志或持久事件。
- 当前代码中的扫描上限与 `policy-v01.md` 的文字存在差异，实施前须核对契约并按影响更新文档，不借此放宽无关规则。

## A：提高单属性长度上限

- 做法：将 2,048 字符阈值提高到例如 8,192，仍把完整值纳入既有指纹，并保持属性数量和总字符预算。
- 范围：`packages/browser-chrome/src/control-document.mts`、策略上下文测试与文档。
- 优点：改动小，完整内容继续参与原有绑定；可覆盖此次 3,186 字符的属性。
- 缺点：只延后同类问题，超过新阈值仍会暂停；更多原始数据进入指纹计算的中间结构。
- 风险：必须校验现有总预算与异步确认重检；不能由探针结果推定所有页面均可处理。

## B：对有界超长属性值计算完整摘要（推荐）

- 做法：保留短属性的现有行为；对长度在 2,049 至 65,536 字符之间的属性，将**完整值**计算 SHA-256 摘要，并将属性名、长度、摘要以无歧义结构纳入目标指纹；按原始长度计入现有总预算。超过单项或总预算、属性名超限等情况仍标记不完整。属性数量、扫描、敏感检测和目的地规则不变。
- 范围：`packages/browser-chrome/src/control-document.mts`、浏览器上下文和策略确认测试、契约说明与真实站点探针。
- 优点：覆盖更多大型属性，不把完整长值放入最终指纹材料；对完整值任何变化重新计算摘要，维持变更绑定。
- 缺点：实现涉及异步摘要和有界资源计算；需要明确编码、边界、异常处理和摘要与普通值的类型区分。
- 风险：哈希不代表属性内容无关或可信；仍须针对超限、巨大输入、摘要失败和确认前后变化测试。仅有指纹变更并不能推断属性的业务语义。

## C：仅对指定属性使用完整摘要

- 做法：只对 `data-i18n-ui` 的有界超长值采用方案 B 的完整摘要；其他属性仍遵守 2,048 字符限制。
- 范围：同 B，但增加明确的属性名白名单和边界测试。
- 优点：行为变化范围较小，可验证本次独立探针场景。
- 缺点：针对站点实现细节；其他同类属性仍阻塞，白名单维护成本持续增加。
- 风险：属性名不是安全属性；即便使用白名单，也必须绑定完整值并保持敏感检查与确认，不能忽略该属性。

## 建议

推荐 **B**：对完整属性值做有界摘要，同时保持原有策略和确认边界；它针对的是超长数据的表示方式。完成后仍需回到真实 Open Library 试用，且独立探针的成功不能代替用户会话验收。若优先最小改动，可选 A；若优先限制行为变更范围，可选 C。

本阶段不实施。请选择方案后，单独编写文件级计划并等待确认。
